Full project details

AI Appointment Scheduler

A booking platform for faculty office hours with an AI assistant that answers from a knowledge base with citations and only acts after the user confirms. University names, people and policies in the demo are fictional.

Live demo

Features

Students

  • Browse every faculty member's open office hours on a week, month or list calendar (week on wide screens, month on phones) with a status legend that filters
  • Book in one click from the calendar or the faculty directory, with an optional note and a 10-second undo
  • Reschedule within the same faculty member, cancel with an optional reason the faculty member sees, and edit notes
  • Export to a calendar app (.ics), get a day-before reminder, and see live notifications
  • Self-register (optionally restricted to a domain) and page through the full history of past and cancelled appointments

Faculty

  • Publish availability as single slots, back-to-back runs or weekly repeats
  • Close, reopen or delete unbooked slots, and move or cancel students' appointments
  • Undo recent changes for 15 minutes, backed by an action journal

Admins

  • An overview plus searchable, pageable users, appointments, slots and a cross-user activity log (filters run in the database)
  • Create faculty, correct user details, cancel appointments and deactivate accounts, which cancels their upcoming appointments

AI assistant

  • Answers policy and how-to questions with citations; each role retrieves only its own guide
  • Prepares bookings, reschedules, cancellations, note changes, weekly slot patterns and undo as confirmation cards that run only after you confirm
  • Understands follow-ups, relative dates and Arabic

Everyone

  • Account settings for name and password; a password change signs out other devices and keeps the current one
  • Notifications with colour-coded kinds, a live badge that shows an unread breakdown on hover, an alert card for important arrivals, and mark-all-read or clear-read
  • Booking rules in one place: book at least an hour ahead, change up to an hour before, no changes after the start, and at most 2 upcoming appointments per faculty member; shown in a popover and stated by the assistant
  • One-click guest sign-in for student, faculty and admin, with a weekly sample-data reset

Technical details

Architecture

  • Next.js 16 (App Router), React 19, TypeScript in strict mode and Tailwind CSS 4
  • Route handlers validate every input with Zod and return typed errors
  • One write path: every change goes through lib/services (checks, then a transaction that journals the change for undo); business limits live in one lib/rules.ts that feeds enforcement, the rules popover, the assistant's prompt and the tests
  • All times use the campus time zone (IANA, DST-safe), including what the assistant sees

Data and concurrency

  • PostgreSQL 16 with pgvector through Prisma 7; a unique key on (faculty, start time) prevents overlapping slots, and cancelled appointments stay as history
  • A slot is claimed with a conditional update inside a transaction; the student's row is locked so overlap and limit checks cannot race, and an advisory lock protects the last-admin rule
  • Race tests run against a real Postgres

AI assistant

  • Retrieval: the knowledge base is chunked (about 600 tokens, about 12% overlap), embedded as 384-dimension vectors, and the nearest 8 chunks by cosine similarity are fetched from pgvector, filtered by role in SQL
  • Generation: DeepSeek through the Vercel AI SDK with 15 role-scoped tools (read and write) and streamed answers with citations
  • Safety: tools only return proposals, a confirmation calls the same REST API a click would, client-sent tool output is discarded, and chat history stays in the browser
  • The prompt layout keeps about 93% of input tokens cached, and replies start in about 2.5 seconds
  • Evaluation: a retrieval eval of about 20 golden questions and a live suite of about 115 checks (injection, data leaks, scope, ambiguity, Arabic, multi-turn) that gates prompt changes

Security

  • Roles and account deactivation are re-checked from the database on every request
  • Nonce-based CSP and HSTS, JSON-only request bodies, and bcrypt password hashing
  • Rate limits (Upstash) on sign-in, password changes and the assistant
  • Names reject hidden characters, and calendar exports keep user text inside its field (a bug found in an edge-case review and fixed under test)
  • Sentry error tracking with personal-data collection off; Dependabot, CodeQL and a CI dependency audit

Testing and delivery

  • 270 unit, 184 integration (against Postgres) and 67 end-to-end tests, including axe accessibility scans in both themes and phone-width layout checks
  • CI on every push: dependency audit, lint, typecheck, unit, integration, end-to-end and a production build, with CodeQL alongside
  • Multi-stage Docker image on Render with Neon (Postgres and pgvector), expand-then-contract migrations through a migrate workflow, a monitored health check, a weekly sample-data reset, and Neon restore points

Full project details

Student-Faculty Services v2

A full rewrite of my senior capstone: students book time in faculty office hours, and faculty manage their hours, closures and booking rules. An unofficial student project; faculty names, ranks and colleges come from AAU's public staff pages, and everything else in the demo is sample data.

Live demo

Features

Students

  • Faculty directory: search by name or college, with each person's next free time
  • Faculty profiles: details, weekly office hours with their rooms or online meetings, and rating averages once there are three ratings
  • Booking grid for the next 7 days: pick a session length (5, 15, 30 or 45 minutes) with free-slot counts per length; times inside a faculty member's minimum notice show as "Too soon"
  • Limits: at most 5 upcoming appointments, one per faculty member per day, and no overlaps
  • Cancel with a 10-second undo
  • Waitlist when nothing is free (up to 5 at once): one alert when a time opens, in the app and by email if enabled
  • Ratings after an attended appointment: three 1-5 criteria within 14 days, anonymous to faculty
  • Reminders the day before each appointment and before the rating window closes, plus optional email with a verified address
  • Profile with name, major and photo; sign-up with an AAU-format student ID and a "Suggest an ID" helper

Faculty

  • Dashboard with today's appointments and Close now for emergencies
  • Weekly office-hours blocks (1.5 hours, up to two a day), each in a campus room or online; editing or removing one previews which bookings it would cancel
  • Closures: close a range of time with a preview of who is affected; a 10-second undo restores their bookings, and students are told once it is final
  • Booking rules: minimum notice, session lengths offered, and a gap around each appointment; they apply to new bookings only
  • Approvals: mark finished appointments attended or not, with an optional report, which opens rating for the student

Everyone

  • Notification bell (checked every minute while the tab is visible): bookings, cancellations, closures, reminders, approvals, rating requests and "a time is free"; shows the newest 30 with Show older and Clear read
  • Light and dark themes, phone layouts, and short tips on every page
  • Demo: one-click student and faculty accounts, or sign in as any of the 155 faculty and 200 sample students; the demo resets itself weekly

Technical details

Architecture

  • React 19, TypeScript, Vite, React Router and TanStack Query on the front end
  • A layered, framework-free PHP 8.4 API: router, controllers, services and repositories over PDO, with 46 REST endpoints (28 of them write endpoints)
  • MariaDB 11.4 with 13 tables (11 foreign keys, 11 CHECK constraints and 4 unique keys)
  • All times use Asia/Dubai through one clock that tests can freeze

Booking correctness

  • One transaction locks the student row, then the faculty row (always in that order, so bookings cannot deadlock) and checks ten rules
  • Tested three ways: a test holding a shared lock from a second connection, eight students racing for one slot over real HTTP (exactly one wins), and every rule checked in SQL at four times of the week; the race test fails without the lock
  • Undo: a cancelled time is held for 15 seconds (the interface offers 10), the other side's notification is dated at the end of the window, and undo re-checks every rule under the same locks; an undo racing seven bookings always wins

Reminders, email and upkeep

  • Reminders are claimed with a conditional update, so each is created once; optional emails go through an outbox, are scheduled ahead, and one whose reason is gone is never sent
  • Email addresses are verified with a click that needs a real button press, so mail scanners cannot confirm them
  • New database migrations, the weekly demo reset and reminders run automatically on the first request that needs them, under database locks; a test proves the original schema plus every migration equals the current schema

Security

  • Prepared statements (real server-side prepares) for every query that takes user input; ownership is checked in the SQL itself
  • A CSRF token is required on all 28 write endpoints; login throttling by email and IP; strict sessions with a new ID on login and logout
  • Uploaded photos are re-encoded to WebP, which drops metadata and hidden payloads; security headers are set on responses

Testing and delivery

  • 273 PHPUnit tests (unit, feature tests through the real router, and real-HTTP tests through Apache), 134 Vitest tests, and 14 Playwright tests that each run on desktop and phone with axe accessibility checks in light and dark mode
  • The booking race test was proven by removing the lock: without it, it produced double bookings; Lighthouse scores 100 for accessibility and best practices on the login page
  • GitHub Actions runs the web and API checks, integration tests and a production-layout check, and deploys only when everything passes; local development and CI use the same MariaDB version as production
  • A README with architecture and data-model diagrams, a handoff guide for new developers, and a deploy guide with the migration procedure
